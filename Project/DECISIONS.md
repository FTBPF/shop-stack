# Technical Decisions and Implementations

This document explains the main database design and implementation decisions in Shop Stack, focusing on the reasoning behind choices that involve trade-offs, business rules or future maintenance.

## 1. Load Batch Management

### UUIDv7 as the load identifier

**Decision:** Use UUIDv7 as the primary key of `load_batches`, instead of an auto-incrementing integer.

**Reasoning:**

- UUIDv7 includes a time-based component, making identifiers roughly sortable by creation time.
- Identifiers can be generated by the application before inserting the batch into the database.
- UUIDs avoid relying on the database to generate sequential identifiers.

### UTC timestamps

**Decision:** Generate the batch start timestamp in Python using a timezone-aware UTC datetime.

**Reasoning:**

UTC provides a consistent reference timezone, avoiding ambiguity when comparing timestamps generated across different environments or timezones. Using timezone-aware datetimes also ensures compatibility with PostgreSQL's `TIMESTAMPTZ` type.

### Load status and timestamp constraints

```sql
CONSTRAINT ck_load_batches_status CHECK (load_status IN ('running', 'succeeded', 'failed')),

CONSTRAINT ck_load_batches_timestamps CHECK (
    (load_status = 'running' AND completed_at IS NULL)
    OR (load_status IN ('succeeded', 'failed') AND completed_at IS NOT NULL)
)
```

**Decision:** Restrict batch statuses to `running`, `succeeded` and `failed`, and enforce consistency between the status and completion timestamp.

**Reasoning:**

These statuses represent the lifecycle of an ETL execution. A running batch has not finished and therefore has no completion timestamp, whereas a successful or failed batch must have one.

These constraints prevent inconsistent batch states from being stored.

## 2. Products

### Price constraints and numeric precision

```sql
CONSTRAINT ck_products_cost CHECK (cost >= 0),
CONSTRAINT ck_products_retail_price CHECK (retail_price >= 0)
```

```sql
cost NUMERIC(10, 2) NOT NULL,
retail_price NUMERIC(10, 2) NOT NULL
```

**Decision:** Use `NUMERIC(10, 2)` for monetary values and prevent negative costs and retail prices.

**Reasoning:**

`NUMERIC` provides exact decimal representation, which is preferable to floating-point types for monetary values.

Negative costs and retail prices are considered invalid for the intended meaning of these fields, so the CHECK constraints enforce this rule directly in the database.

## 3. Orders

### Order status CHECK constraint

```sql
CONSTRAINT ck_orders_status CHECK (status IN (
    'Cancelled',
    'Complete',
    'Processing',
    'Returned',
    'Shipped'
))
```

**Decision:** Restrict order statuses to the distinct values found in the source data.

**Reasoning:**

After inspecting the distinct statuses in the source data, these five values were identified.

Since these statuses represent established order states and are not expected to change, the decision was to treat them as a controlled set of valid states rather than allowing arbitrary text values.

If a new status is introduced, the CHECK constraint must be updated and the schema change applied. This requires an intentional change.

## 4. Order Items

### Removing `user_id`

**Decision:** Remove `user_id` from `order_items`.

**Reasoning:**

The user associated with an order item can already be identified through its relationship with `orders`, using `order_items.order_id` to retrieve `orders.user_id`.

Storing `user_id` again would duplicate information and introduce the possibility of inconsistencies between the user associated with the order and the user stored in its items.

### Removing `num_of_items`

**Decision:** Remove `num_of_items` from `order_items`.

**Reasoning:**

The number of items in an order can be obtained by counting the corresponding rows in `order_items`.

Storing this value separately would duplicate information and introduce the possibility that the stored count becomes inconsistent with the actual order items.

### Sale price constraint

```sql
CONSTRAINT ck_order_items_sale_price CHECK (sale_price >= 0)
```

**Decision:** Prevent negative sale prices.

**Reasoning:**

A sale price represents the amount charged for an item and should not be negative. The constraint prevents invalid monetary values from being stored.

### Order item status CHECK constraint

```sql
CONSTRAINT ck_order_items_status CHECK (status IN (
    'Cancelled',
    'Complete',
    'Processing',
    'Returned',
    'Shipped'
))
```

**Decision:** Use the same allowed status values as the `orders` table.

**Reasoning:**

The source data contains the same set of distinct status values for order items. Restricting both tables to this set keeps the accepted statuses consistent.

## 5. Events

### Event type CHECK constraint

```sql
CONSTRAINT ck_events_event_type CHECK (event_type IN (
    'home',
    'department',
    'product',
    'cart',
    'purchase',
    'cancel'
))
```

**Decision:** Restrict event types to the distinct values found in the source data.

**Reasoning:**

These values were identified by inspecting the distinct event types in the source data.

Event types are more likely to change as the website evolves. For example, adding a new page or functionality may require introducing another event type.

The decision was to enforce an explicit list of allowed event types, requiring the schema to be updated whenever a new event type is introduced.

This prevents unexpected values from silently entering the database and makes changes to tracked website interactions an intentional database change.

### Nullable `user_id`

```sql
user_id INT REFERENCES users(id)
```

**Decision:** Allow `user_id` to be NULL.

**Reasoning:**

Users can access the website anonymously without having an account. In these cases, the events they generate are not associated with a registered user, so `user_id` is NULL.

Allowing NULL values ensures that anonymous user activity can still be recorded without requiring a user record to exist.

### Session and sequence information

```sql
session_id TEXT NOT NULL,
sequence_number INT NOT NULL
```

**Decision:** Require every event to have a session ID and a sequence number.

**Reasoning:**

- `session_id` identifies the session in which the event occurred, allowing events belonging to the same session to be grouped together.
- `sequence_number` indicates the order in which events occurred within a session.

These fields allow session activity to be tracked and events to be ordered, even when they are not associated with a registered user.

## 6. Load Tracking Across Tables

All source tables contain a `load_id` foreign key referencing `load_batches(load_id)`.

**Decision:** Associate every loaded record with the ETL batch that last inserted or updated it.

**Reasoning:**

This provides traceability between the data and the ETL execution that processed it.

By joining a record with `load_batches`, it is possible to retrieve the timestamp and status of the batch associated with its most recent load.

The trade-off is that only the most recent batch association is retained on each record. Previous associations are not preserved when a record is updated.
